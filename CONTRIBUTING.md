# Contributing

The corpus in `WIKI/` is the source of truth. Everything else — the JSON database,
the graph, the search index, the exports, the site — is generated by the pipeline.
Do not edit generated files by hand; edit the Markdown and rebuild.

## The one command

```powershell
$env:PUBLIC_SITE_URL="https://blender-mcp-wiki.refertur.net"
python WIKI/scripts/run_all.py
```

It must end in `PIPELINE GREEN`. That string is the acceptance criterion, and it
is checked in CI on every push.

## Adding an article

1. Put the Markdown in the right category folder under `WIKI/`.
2. Fill the frontmatter. Required: `id`, `lang`, `category`. Recommended:
   `type`, `status`, `tags`.
3. Write it against `WIKI/templates/DEPTH.md`. The contract sets the required
   sections and the depth floor — 450 words of prose **or** 8 code blocks.
4. Run the pipeline.

Two rules in `DEPTH.md` matter more than the rest:

**Do not invent API names, versions, URLs or flags.** A plausible invention is
worse than an honest gap, because a reader cannot tell the difference. If you are
not sure of a parameter, write the general principle and mark it:

```markdown
> [!NOTE]
> The exact key name changed between versions — check the tool's own docs.
```

**Do not pad.** The depth floor is a floor, not a target. An article that cannot
reach it without filler should stay `status: stub`, which is an honest label
rather than a claim.

## Translating

`WIKI/templates/TRANSLATION_RU.md` is the contract.

The translation quality field is not decoration — it decides whether the article
gets a page:

| `translation:` | Meaning | Published |
|---|---|---|
| `human` | translated and reviewed by a person | yes |
| `ai` | a real translation produced with machine assistance, not human-reviewed | yes |
| `template` | the original text with a language header | **no** |
| `legacy` | superseded, kept for history | **no** |

Do not mark a translation `template` to make it visible. Untranslated mirrors are
kept in the repository as a translation backlog precisely so nobody has to fake
one.

## Before you push

```powershell
python WIKI/scripts/run_all.py     # PIPELINE GREEN
cd web; npm run all                # 33 tests + 3 gates + preflight
cd web; npm run check              # 0 type errors
```

`npm run all` includes the SEO and consistency gates and the preflight, which
fails if the canonical origin is not the one the configuration expects.

## Commit convention

```
feat|fix|docs|refactor|test|build|ci|chore(scope): subject
```

The subject says what changed. Describe why in the body — specifically what was
measured, not that work happened.

## What you must not do

- **Never delete an article without asking the owner first.** Twice. There is a
  protocol for this and it exists because work has been lost.
- **Never put a secret in a file.** `.env` is the only place a key lives;
  `.env.example` ships with empty values and is the only env file committed.
- **Never edit `WIKI/db/`, `WIKI/site/data/` or `web/dist/`.** They are generated
  and gitignored.
- **Never widen the CSP.** It has no `'unsafe-inline'` on purpose; a gate fails
  the build on any inline event handler.

## Adding a pipeline step

Edit `WIKI/scripts/run_all.py`. Put a check in `CORE` and give it `gate=True` if
a failure should stop the build — and then make sure it *can* fail. A check that
only reports is not a gate, and calling it one in the changelog is worse than not
having it.
