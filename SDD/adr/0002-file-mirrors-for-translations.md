# ADR 0002 — Переводы как файловые зеркала, а не оверлеи

- **Статус:** принято
- **Дата:** 2026-09-24

## Контекст
Нужно 5 языков поверх ~182 оригиналов. Варианты: (а) хранить полные копии в
`multilang/{lang}/**`, (б) оверлей «только изменённые строки» + fallback на оригинал,
(в) генерировать переводы на лету из словаря.

## Решение
Файловые зеркала: `multilang/{lang}/{category}/{тот же файл}.md`, ID = `{stem}__{lang}`.

## Последствия
- **Плюсы:** каждая статья — обычный валидный markdown, который можно читать/править/переводить
  в любом редакторе; поиск, сайт, экспорт работают по единому коду без ветвлений;
  frontmatter `translation: human|template|legacy` честно показывает качество.
- **Минусы:** 815 файлов-переводов (×4 к объёму контента) — это цена за простоту;
  grep по репозиторию даёт дубли; относительные ссылки внутри зеркал указывают на файлы
  с другой глубины, поэтому **зеркала исключены из проверки ссылок** (`validate.py` §9),
  иначе валидатор тонул бы в ложных срабатываниях.
- **Ловушка, найденная тестами (2026-09-28):** при переименовании оригинала
  `01_primitive_creation.md` → `01_geometry_basics.md` зеркала остались со старым именем.
  Получилось 5 «сирот» — переводов без оригинала, которые попадали в БД, сайт и API как
  самостоятельные статьи. Поэтому введён инвариант 2 (`validate.py` §11) и тест
  `test_multilang_parity`.
- Альтернатива (б) отвергнута: она требует собственного резолвера оверлеев в билдере, сайте,
  API и экспортах — четыре реализации вместо одной. Вернуться к ней имеет смысл только
  при переводе всего корпуса.
