# ADR 0003 — Статический сайт с чанками и предрасчётным графом

- **Статус:** принято
- **Дата:** 2026-09-25

## Контекст
БД выросла до ~9.4 МБ JSON. Статический сайт грузил её целиком (`wiki_database.json`),
а `graph.html` считал раскладку сил в браузере — O(n²) по всем нодам и связям.

## Решение
1. `site/data/meta.json` — лёгкий индекс (карточки списка, поиск).
2. `site/data/chunks/entries_{category}.json` — полные записи по категориям; `app.js`
   подгружает нужный чанк при открытии статьи.
3. Позиции графа считаются в `build_graph.py` (золотой угол + секторы категорий) и кладутся
   в `graph.json`; браузер только рисует.

## Последствия
- **Плюсы:** первая отрисовка списка — сотни КБ вместо 9.4 МБ; граф детерминирован
  (одинаковый при каждой сборке, диффы видны); O(n²) ушёл из браузера.
- **Минусы:** два уровня данных (`meta.json` + чанки) — появился риск рассинхрона.
  Поэтому добавлен гейт `validate.py` §7: `meta.total == сумма chunks == db.total_entries`,
  и тест `test_meta_and_chunks_match_db`. Старый `wiki_database.json` в `site/data/` оставлен
  как fallback, если `meta.json` не найден (и как вход для API-режима).
- **Учтено:** имена чанков не хэшируются, поэтому `Cache-Control: immutable` применять нельзя —
  используется `max-age=300, must-revalidate` + ETag (иначе после пересборки браузер год
  отдавал бы устаревшие чанки).
