# ADR 0005 — Astro static output on Cloudflare Pages, static site under a subdomain

- **Статус:** принято (пересмотрено 2026-10-01, первоначально решалось про Workers)
- **Дата:** 2026-10-01

## Контекст
Требования: сайт на Astro, размещаемый на Cloudflare, доступный по поддомену
`blender-mcp-wiki.refertur.net`, с полной SEO-оптимизацией и оптимизацией под
языковые модели. Обязательное условие — чтобы поисковики и агенты читали
контент без выполнения JavaScript.

Топология DNS, установленная read-only разведкой (`dns-recon.mjs`):

```
refertur.net   NS: ns1/ns2.timeweb.ru, ns3/ns4.timeweb.org
               → зону обслуживает Timeweb, регистратор — другой (Spaceship)
blender-mcp-wiki.refertur.net → не резолвится, записи нет
```

Зона apex обслуживается **Timeweb**, а не Cloudflare. Значит поддомен
подключается через CNAME в панели Timeweb — это внешний DNS, и Cloudflare
о Domain Zone тут не имеет.

## Решение
Astro 7 в режиме `output: 'static'`, публикация в **Cloudflare Pages**
(`wrangler pages deploy dist --project-name=blender-mcp-wiki`), кастомный домен
`blender-mcp-wiki.refertur.net` через CNAME, поиск — Pagefind (индекс на сборке).

## Последствия

**Почему Pages, а не Workers со статическими ассетами**
Первая версия этого ADR выбрала Workers, и это было неверно для данной задачи.
Повторная оценка:
- Цель — кастомный поддомен при внешней DNS-зоне. У Pages есть
  first-class привязка и верификация кастомного домена; у Workers это тоже
  есть, но сценарий с внешней зоной там не документирован как основной.
- `wrangler pages deploy` — документированный путь именно для этого случая.
- Отказ `@astrojs/cloudflare` от Pages касается **только on-demand
  рендеринга** (SSR). Статический вывод адаптера не требует вообще, поэтому
  ограничение на нас не распространяется. Это важно: сначала я прочитал это
  ограничение как «Pages больше не вариант», что было слишком широким прочтением.

**Почему static, а не SSR**
- Контент не меняется между сборками → предрендер быстрее и дешевле.
- Краулер получает HTML с первого ответа: часть агентов не выполняет JS.
- Нет рантайма: нет Cold Start, нет среды, нет секретов.

**Цена**
- Публичный полнотекстовый поиск с произвольными фильтрами остался в
  локальном Python-API (`:8099`). На сайте — Pagefind по телу статей.
- Каждая правка контента = пересборка и деплой (~90 с).
- Домен фиксируется на момент сборки (`PUBLIC_SITE_URL`); смена домена требует
  пересборки, иначе canonical разъедется.

**Конфигурация, проверенная на живом `wrangler dev`**
- `_headers` в `public/` — работает на Pages для статических ассетов:
  security-заголовки, CSP (с `wasm-unsafe-eval` для Pagefind),
  `Link: rel="describedby"`, кэш.
- `.md`-файлы отдаются как `text/markdown` — проверено замером.
- 2664 файла, максимум 978 КБ: в пределах лимитов Pages (20 000 файлов,
  25 МБ на файл).

**Что осталось за пределами автоматизации**
CNAME в зоне Timeweb. Cloudflare примет домен и покажет `pending`, но имя
не начнёт резолвиться, пока запись не создана. Сообщать «задеплоено» до
`dig` — прямая ложь; статус — «pending DNS».

**Что не выбрано**
- Cloudflare Workers static assets: сценарий с внешней DNS-зоной не основной.
- NS-делегация поддомена Cloudflare: тяжелее и рискованнее, CNAME достаточно.
- SPA с клиентским рендером: недоступен без JS — провал по SEO.
